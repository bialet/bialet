Why Bialet?#

Bialet makes a specific trade-off: maximum simplicity for a narrow but common set of use cases. This page explains what that means, when it’s a good fit, and how it compares to other tools.

The Philosophy#

Most web frameworks optimize for flexibility. They give you middleware stacks, ORM layers, routing DSLs, template engines, and configuration files — all designed to handle any scenario you might encounter.

Bialet optimizes for getting things done on a single server. It bundles the HTTP server, the database, and the language runtime into one binary. Your app is a directory of .wren files and a SQLite database. That’s it.

If your needs fit within Bialet’s scope, you get an experience that is hard to assemble elsewhere: zero-config development, single-command deployment, and no dependency management.

If your needs grow beyond that scope, you’ll want a different tool — and that’s okay.

When to Use Bialet#

  • Prototypes and MVPs — Go from idea to working app in minutes. No setup, no boilerplate.

  • Internal tools and dashboards — Admin panels, reporting UIs, data browsers. The database is already there.

  • Simple CRUD applications — Blogs, polls, task trackers, form-based apps.

  • Learning web development — Skip the configuration and focus on HTML, SQL, and basic programming concepts.

  • Single-server deployments — Small to medium traffic sites on a VPS or shared host.

When NOT to Use Bialet#

  • High-traffic public sites — Bialet is a single-process server. It can’t distribute load across multiple machines.

  • Real-time applications — No WebSocket or Server-Sent Events support. Polling works for simple cases, but it’s not ideal.

  • Large teams with existing infrastructure — If you already have PostgreSQL, Redis, and a CI pipeline, Bialet’s simplicity isn’t buying you much.

  • Microservices — Bialet is designed for monolithic apps on a single server.

  • Heavily interactive UIs — Drag-and-drop editors, optimistic updates, and offline support need client-side state. Bialet re-renders the page instead.

  • Complex auth flows — Bialet supports basic auth and sessions, but not OAuth, SAML, or multi-factor authentication out of the box.

The Language Bet#

Embedding Wren is the decision that makes Bialet Bialet. The VM is small, dependency-free C, so it links into the same binary as the server and SQLite; the language is class-based and object-oriented, so HTML, SQL, and application logic live in one file without a build step.

It is also the biggest thing Bialet asks of you. There is no package registry, no LSP or autocomplete yet, and most developers have never written Wren. The Wren guide states those costs plainly, and Wren for JavaScript and Python developers is most of the mapping you need to start.

Comparisons#

Bialet vs. React / Next.js#

React is a client-side UI library; Next.js is the framework around it, adding routing, server rendering, and a build pipeline. Both are built to ship a JavaScript application to the browser and keep it running there. Bialet renders HTML on the server for every request and sends no component runtime at all.

React wins wherever the page has to react without a round trip: rich forms, in-place editing, shared client state, offline behavior. It also wins on hiring and libraries. Next.js pulls rendering back to the server, which narrows the gap, but you still own the toolchain, the hydration model, and the bundle. Bialet’s inline HTML looks like JSX at a glance — JSX to Bialet lists the differences that matter when porting.

Bialet vs. Vue#

Vue is the gentler of the two mainstream client frameworks: single-file components, a reactivity system, and Nuxt for server rendering. The difference from Bialet isn’t syntax — it’s where state lives. In Vue the page is a component tree kept up to date in the browser; in Bialet the page is regenerated on the server and the state is whatever is in the database and the URL.

For tables, forms, and links — most internal tools — Bialet does the same job with no build step and no hydration. When you need live filtering, in-place edits, or a genuinely app-like screen, Vue is the lighter of the two SPA frameworks, but it is still an SPA. A server-rendered Nuxt app sits closest to Bialet; the price is the toolchain you were trying to avoid.

Bialet vs. Static Site Generators#

Static site generators (Hugo, Jekyll, Eleventy) produce HTML files at build time. Bialet generates HTML at request time and includes a database.

If your site has no dynamic data and no forms, use a static site generator. If you need a database, forms, or user-specific content, Bialet is the lighter alternative to a full backend framework.

pdo_sqlite is compiled into most PHP builds, so “PHP with SQLite” is a real one-file setup that needs no database server. What Bialet adds is the executable: no web server to configure, no php.ini, no FPM worker pool, and no Composer step. What PHP adds is a hosting industry, a large ecosystem, and plenty of people who already know it.

PHP wins on ecosystem, hiring, and hosting. Bialet wins on one artifact that runs the same way on every machine.

Go is the better tool when you need real parallelism, a typed codebase, or a library for everything. Bialet is the better tool when you want to edit a .wren file and refresh, keep one small binary, and not think about compilation or dependencies at all.

Bialet vs. PocketBase#

PocketBase is also a single executable with SQLite behind it, but it is a backend-as-a-service, not a template engine. It ships an admin UI, a collection editor, auth, file storage, REST and realtime APIs, and a JavaScript SDK. Bialet ships a language and expects you to write the HTML.

Choose PocketBase when you want a ready-made backend and a JavaScript frontend. Choose Bialet when the app is server-rendered pages and you want to write the HTML and SQL yourself.

Bialet vs. Express / Flask#

Express and Flask are deliberately minimal: you add only what the app needs. A minimal Express app can return HTML strings and talk to SQLite through a driver; Flask ships Jinja2, and Python’s standard library already has sqlite3. Neither requires an ORM or a database server.

What neither includes is the wiring: sessions with CSRF protection, database migrations, a request/response API, and a deployment story. Bialet’s difference is that all of it is in the binary and already connected.

Express and Flask give you more control over the stack and a language people already know. Bialet gives you fewer decisions and fewer moving parts.

Bialet vs. HTMX plus a backend#

If SPA complexity is the problem but a new language is not worth it, HTMX in front of Flask, Express, or Go gives you partial updates without a JavaScript build. That is a legitimate answer, and Bialet does not beat it on flexibility: you keep a language and ecosystem you already know.

Bialet differs in what is already assembled — server, database, sessions, CSRF, migrations — and in rendering whole pages by default instead of fragments. If you already have a backend you like, adding HTMX is less work than adopting Bialet. If you are starting from nothing on one server, Bialet removes more pieces.

Bialet vs. Django / Rails#

Django and Rails are full-stack frameworks with ORMs, admin interfaces, migrations, and extensive ecosystems. Bialet is full-stack in a different way: it bundles the essentials, nothing more.

If you’re building a complex, long-lived application with a team, Django or Rails are better choices. If you’re building something simple today, Bialet gets you there faster.

The Trade-off#

Bialet is intentionally limited. It doesn’t have:

  • Multi-server horizontal scaling

  • WebSockets

  • Background job queues (beyond Cron)

  • A plugin ecosystem

  • PostgreSQL / MySQL support

  • An ORM

  • OAuth or social login

What it does have is everything you need to build a data-driven website in a single binary. For many projects, that’s exactly the right trade-off.
